# Глава 8. Арифметика в компьютерах: числа с плавающей точкой

## 8.1. Проблема

Откройте Python (или JavaScript, или почти любой другой язык программирования) и вычислите:

```python
>>> 0.1 + 0.2
0.30000000000000004
```

Результат — не $0.3$, а $0.30000000000000004$. Ошибка крошечная (в $16$-м знаке после запятой), но она есть. Почему?

Ответ: компьютеры хранят числа **в двоичной системе**, и дробь $0.1_{10}$ не имеет конечного двоичного представления — точно так же, как $\frac{1}{3}$ не имеет конечного десятичного представления (§5.1).

---

## 8.2. Дроби в двоичной системе

В главе 1 (§1.7) мы видели, что дробная часть числа записывается с помощью отрицательных степеней основания:

$$0.d_1 d_2 d_3 \ldots_{(2)} = d_1 \cdot 2^{-1} + d_2 \cdot 2^{-2} + d_3 \cdot 2^{-3} + \ldots$$

Пример: $0.11_2 = \frac{1}{2} + \frac{1}{4} = 0.75_{10}$.

### Какие дроби имеют конечную двоичную запись

По аналогии с десятичной системой (§5.1): дробь $\frac{p}{q}$ (в несократимом виде) имеет конечную двоичную запись тогда и только тогда, когда $q$ — степень двойки: $q = 2^n$.

| Дробь | Десятичная | Двоичная | Конечная? |
|:-----:|:----------:|:--------:|:---------:|
| $\frac{1}{2}$ | $0.5$ | $0.1_2$ | Да |
| $\frac{1}{4}$ | $0.25$ | $0.01_2$ | Да |
| $\frac{3}{8}$ | $0.375$ | $0.011_2$ | Да |
| $\frac{1}{5}$ | $0.2$ | $0.0\overline{0011}_2$ | **Нет** — бесконечная! |
| $\frac{1}{10}$ | $0.1$ | $0.0\overline{0011}_2$ | **Нет** — бесконечная! |

### Перевод $0.1_{10}$ в двоичную систему

Алгоритм: последовательно умножаем дробную часть на 2, записываем целую часть результата.

| Шаг | Дробная часть | $\times 2$ | Целая часть (двоичная цифра) |
|:---:|:-------------:|:----------:|:----------------------------:|
| 1 | $0.1$ | $0.2$ | $0$ |
| 2 | $0.2$ | $0.4$ | $0$ |
| 3 | $0.4$ | $0.8$ | $0$ |
| 4 | $0.8$ | $1.6$ | $1$ |
| 5 | $0.6$ | $1.2$ | $1$ |
| 6 | $0.2$ | $0.4$ | $0$ ← повторение шага 2 |

Дробная часть $0.2$ повторилась — начался цикл. Результат:

$$0.1_{10} = 0.0\overline{0011}_2 = 0.00011001100110011\ldots_2$$

Бесконечная периодическая двоичная дробь. Компьютер не может хранить бесконечное число цифр — он **обрезает** дробь, и возникает ошибка округления.

## 8.3. Формат IEEE 754

Стандарт IEEE 754 определяет, как компьютеры хранят дробные числа. Самый распространённый формат — **double precision** (двойная точность, 64 бита).

### Структура 64-битного числа

64 бита разделены на три поля:

| Поле | Биты | Что хранит |
|------|:----:|------------|
| Знак | 1 бит | $0$ = положительное, $1$ = отрицательное |
| Экспонента | 11 бит | Степень двойки (порядок) |
| Мантисса | 52 бита | Значащие цифры |

Число представляется в виде:

$$(-1)^s \times 1.m \times 2^{e - 1023}$$

где $s$ — знаковый бит, $m$ — мантисса (52 бита после двоичной точки), $e$ — экспонента (целое число от $0$ до $2047$, со сдвигом $1023$).

### Аналогия: научная нотация

Это похоже на **научную (экспоненциальную) запись** в десятичной системе:

$$6.022 \times 10^{23}$$

Здесь $6.022$ — мантисса (значащие цифры), $10$ — основание, $23$ — экспонента. В IEEE 754 всё то же самое, только основание — $2$, и количество значащих цифр фиксировано.

### Точность

52 бита мантиссы дают примерно $15$–$17$ значащих десятичных цифр. Это значит, что числа, отличающиеся в $16$-м и далее знаках, **неразличимы** для компьютера.

Именно поэтому $0.1 + 0.2$ даёт $0.30000000000000004$: ошибка накапливается в $17$-м знаке.

## 8.4. Типичные ошибки

### Потеря ассоциативности

В математике $(a + b) + c = a + (b + c)$. В компьютерной арифметике — **не всегда**:

```python
>>> (0.1 + 0.2) + 0.3
0.6000000000000001
>>> 0.1 + (0.2 + 0.3)
0.6
```

Результат зависит от порядка сложения! Это происходит потому, что промежуточные округления в разном порядке дают разные ошибки.

### Катастрофическое сокращение

Когда из близких чисел вычитают друг друга, значащие цифры «съедаются», и относительная ошибка резко возрастает.

Пример: вычислим $\sqrt{1000001} - \sqrt{1000000}$.

```python
>>> import math
>>> math.sqrt(1000001) - math.sqrt(1000000)
0.0004999999875000002
```

Точный ответ ближе к $0.0005000000$, но из-за вычитания двух почти равных чисел ($\approx 1000.0005$ и $1000.0000$) мы потеряли несколько значащих цифр.

Обходной путь — преобразовать выражение алгебраически:

$$\sqrt{a} - \sqrt{b} = \frac{a - b}{\sqrt{a} + \sqrt{b}}$$

```python
>>> 1 / (math.sqrt(1000001) + math.sqrt(1000000))
0.0004999999875000001
```

Формула даёт тот же результат с меньшей потерей точности.

### Сравнение дробных чисел

Из-за ошибок округления **нельзя** сравнивать числа с плавающей точкой на точное равенство:

```python
>>> 0.1 + 0.2 == 0.3
False
```

Вместо этого сравнивают с допуском (эпсилон):

```python
>>> abs((0.1 + 0.2) - 0.3) < 1e-9
True
```

## 8.5. Накопление ошибок

Единичная ошибка округления ничтожна ($\sim 10^{-16}$). Но при миллионах операций ошибки **накапливаются**.

### Пример: суммирование

Сложим число $0.1$ миллион раз:

```python
>>> s = 0.0
>>> for _ in range(1_000_000):
...     s += 0.1
>>> s
100000.00000133288
```

Ожидаемый результат — $100\,000$. Фактический — $100\,000.000001\ldots$. Ошибка $\approx 1.3 \times 10^{-6}$ — уже заметная.

### Суммирование Кэхэна

Для борьбы с накоплением ошибок существует **алгоритм Кэхэна** (Kahan summation, 1965): он «запоминает» потерянную часть и компенсирует её на следующем шаге.

```python
def kahan_sum(values):
    s = 0.0
    c = 0.0  # компенсатор потерянных битов
    for x in values:
        y = x - c
        t = s + y
        c = (t - s) - y
        s = t
    return s
```

```python
>>> kahan_sum([0.1] * 1_000_000)
100000.0
```

Точный результат.

## 8.6. Диапазон и специальные значения

### Диапазон

64-битный формат IEEE 754 позволяет хранить числа в огромном диапазоне:

| Характеристика | Значение |
|---------------|----------|
| Наименьшее положительное нормализованное | $\approx 2.2 \times 10^{-308}$ |
| Наибольшее конечное | $\approx 1.8 \times 10^{308}$ |
| Машинный эпсилон | $\approx 2.2 \times 10^{-16}$ |
| Значащих десятичных цифр | $15$–$17$ |

**Машинный эпсилон** ($\varepsilon_{\text{маш}}$) — наименьшее число, для которого $1 + \varepsilon_{\text{маш}} \neq 1$ в компьютерной арифметике. Числа, отличающиеся менее чем на $\varepsilon_{\text{маш}}$ (относительно), неразличимы.

### Специальные значения

Мы уже обсуждали `Inf` и `NaN` в §4.5. Дополним таблицу:

| Значение | Как получить | Свойства |
|----------|-------------|----------|
| `+0.0` и `-0.0` | Обычно | Равны при сравнении, но $\frac{1}{+0} = +\infty$, $\frac{1}{-0} = -\infty$ |
| `+Inf` | `1.0 / 0.0` | Больше любого конечного числа |
| `-Inf` | `-1.0 / 0.0` | Меньше любого конечного числа |
| `NaN` | `0.0 / 0.0` | Не равен ничему, включая себя |

!!! tip "Положительный и отрицательный ноль"
    В IEEE 754 существуют **два нуля**: $+0$ и $-0$. Они равны при сравнении (`+0.0 == -0.0` даёт `True`), но различаются знаковым битом. Это нужно для корректной работы с пределами: $\lim_{x \to 0^+} \frac{1}{x} = +\infty$, $\lim_{x \to 0^-} \frac{1}{x} = -\infty$.

---

!!! abstract "Резюме главы"
    - Компьютеры хранят числа в **двоичной** системе; дроби вида $\frac{1}{10}$ не имеют конечного двоичного представления
    - Формат IEEE 754 (double, 64 бита) хранит число в виде $(-1)^s \times 1.m \times 2^{e-1023}$; точность — около $15$–$17$ десятичных цифр
    - $0.1 + 0.2 \neq 0.3$ — следствие неточного представления, а не ошибка в языке
    - Ошибки округления нарушают ассоциативность; вычитание близких чисел особенно опасно (катастрофическое сокращение)
    - Дробные числа нельзя сравнивать на точное равенство — используйте допуск ($\varepsilon$)
    - При большом количестве операций ошибки накапливаются; алгоритм Кэхэна минимизирует накопление
    - IEEE 754 определяет специальные значения: $\pm 0$, $\pm \infty$, `NaN`
